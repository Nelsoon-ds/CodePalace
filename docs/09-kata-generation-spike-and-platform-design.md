# 09 — Kata Generation Spike & Exercise Platform Design

Written 2026-11-03. Records what a one-week spike showed about LLM-generated, validated exercises, and the design decisions we reached for the platform. It supersedes nothing: it extends [04-ai-and-retrieval.md](04-ai-and-retrieval.md) and [05-data-model-api.md](05-data-model-api.md).

The spike code lives on branch `spike/kata-generation`, folder `runner/spike/` (its `README.md` has the step-by-step detail). It is not on `main`.

## TL;DR

- An LLM can generate an exercise (statement, starter code, reference solution, hidden tests) that passes automated validation. In the latest 10-kata run, **5 of 10 passed all five checks**. Best earlier run: **8 of 10**.
- The validation checks are what make this viable. They caught wrong tests, wrong examples, a reference containing prose instead of code, and ambiguous statements. Without them, most of the failed katas would have shipped.
- The author model and the spec quality decide the pass rate. The remaining failures came from the spec step and from concept ambiguity, not from the test-writing step.
- Product direction: a **shared corpus** of validated exercises. Users browse stored exercises by topic and difficulty, or generate a new one within a fixed set of categories. Each exercise is a generated dataset plus at most two tasks, with hidden tests and optional hints.
- One security gap must be closed before real users: user code can read the hidden suite inside the sandbox.

## 1. The concept

A user picks a topic and difficulty. The platform produces an exercise: a problem statement, a starter template, and a hidden test suite. The user solves it in the editor and sees only pass/fail results. Valid exercises are stored and shared, so compute is not wasted and users can come back to them.

The idea sprang from wanting to practice katas while scaling difficulty up and down and having the material be personally relevant. It is deliberately not an exhaustive platform.

## 2. The spike

### Pipeline

```
 inputs ──► 1 spec ──► 2 template ──► 3 author ──► 4 blind solver ──► 5 validate ──► 6 output
            (LLM)      (platform)     (LLM)        (LLM)              (sandbox)       (files)
```

1. **Spec.** The model returns a structured contract: function name, parameters, rules, examples, edge cases. Schema-enforced.
2. **Template.** The platform builds the starter code from the spec, so the signature cannot drift.
3. **Author.** A stronger model writes the statement, reference solution, and hidden test suite from the spec, with one hand-written few-shot example.
4. **Blind solver.** A separate call sees only the statement and the template, and writes its own solution.
5. **Validate.** Five checks in the existing Docker sandbox (`runner/test-sandbox.js`).
6. **Output.** A `ui` section (what a frontend may see) and a `private` section (suite, reference, spec, check results), plus a CSV.

### The five checks

| Check | Passes when |
|---|---|
| `reference_passes` | The reference solution passes the suite |
| `starter_fails` | A throwing stub fails the suite |
| `examples_match_reference` | Example tests generated by the platform from the spec pass against the reference |
| `mutations_fail` | At least one regex mutation of the reference is caught by the suite |
| `blind_solver_passes` | A solution written from the statement alone passes the suite |

The blind solver is the automated version of Codewars' community beta testing. It is the only check that tests the statement rather than the reference.

### Models

| Call | Model | Thinking |
|---|---|---|
| Spec | `gemini-3.5-flash-lite` | `high` |
| Author | `gemini-3.6-flash` | `high` |
| Blind solver | `gemini-3.5-flash-lite` | default (`minimal`) |

`gemini-3.5-flash` is deprecated and routes to 3.6 Flash. `gemini-3.8-flash` was available and described by Google as the newest Flash model; it was not tested.

### Results history

Rounds are not directly comparable: content, models, and prompts changed between them. Earlier raw outputs were deleted.

| Round | Setup | Result | What it showed |
|---|---|---|---|
| 1 | One call writes everything. Free-text themes. Flash-Lite | 8 of 10 passed | Validation caught a wrong test expectation and a reference containing prose instead of code |
| 2 | Spec-first pipeline, Flash-Lite as author, neutralisation | 1 of 5 passed | Reference and suite disagreed about the rule |
| 3 | Author switched to `gemini-3.6-flash` | 8 of 10 passed. 2 failed before validation (JSON parse). All 8 generated katas passed | The author model was the bottleneck |
| 4 | No temperature, `high` thinking, author schema, few-shot example | **5 of 10 passed.** 0 generation failures | See below |

### Latest run (round 4)

| Check | Passed |
|---|---|
| `reference_passes` | 10 of 10 |
| `starter_fails` | 10 of 10 |
| `mutations_fail` | 10 of 10 |
| `examples_match_reference` | 7 of 10 |
| `blind_solver_passes` | 8 of 10 |

The CSV is saved at `runner/spike/results.csv` on the spike branch.

Why the 5 failures happened:

- **Three katas had broken spec examples.** Two used the wrong argument nesting (`[1,-1,2]` instead of `[[1,-1,2]]`; `[]` instead of `[[]]`), so the function received the wrong arguments. One example was wrong arithmetic.
- **Two katas hit an ambiguity in the concept.** Eight of ten references used stack-top matching. Two used "search for the most recent matching value", which returns `[2]` for `[1, 2, -1]`. The blind solver wrote the stack-top version and failed those suites. The concept text allowed both readings.

Cost per kata: about 2,850 input, 1,550 output, and 8,800 thinking tokens (range 5,700 to 14,300). Thinking tokens were about six times the output.

### Caveats on this evidence

- Ten katas per run cannot show whether a change helped. Round 4 changed several settings at once.
- Only one concept (neutralisation, JavaScript arrays) was tested, so results may not transfer.
- The author step looked solid in round 4. The failures were upstream (spec) and downstream (blind solver on an ambiguous statement).

## 3. Findings

**What worked**

- Spec-first generation, with the platform building the template deterministically.
- Schema-constrained output, which removed the JSON parse failures.
- The independent checks: each caught real errors that a single-pass generator would have shipped.
- A stronger author model with high thinking: the reference passed its own suite in 10 of 10 katas.

**What did not**

- Spec examples encoded as one JSON string for the whole argument list invite double-nesting mistakes.
- Concepts described in one sentence can mean two things. The generated katas split between two semantics.
- Regex mutations are weak. A surviving mutant is often equivalent to the original (for example, `length > 0` versus `>= 0`), so the check requires one kill, not all.
- Low diversity: ten generations of one concept produced near-identical katas.

**Security gap.** User code runs in the same container as the hidden suite and can read `tests/suite.test.mjs`. Verified with a probe from inside the sandbox. A user could read the expected answers. Acceptable for a demo, not for real users. Options: deliver the suite over stdin so it is never on disk, or run a trusted harness outside the user's container.

## 4. Gemini model guidance

From Google's Gemini API docs (read through Context7):

- **No `temperature`, `top_p`, or `top_k`.** Deprecated on Gemini 3.x; ignored on 3.6 Flash and 3.5 Flash-Lite; newer models return HTTP 400. Use a system instruction for determinism instead.
- **Thinking level is the quality dial.** 3.5 Flash-Lite defaults to `minimal`, close to no reasoning. 3.6 Flash defaults to `medium`. Do not combine `thinkingLevel` with `thinkingBudget`.
- **Structured output follows schema key order.** Put reasoning-style fields first, make all fields required, and do not specify field order in the prompt.
- **Prompting.** Be concise and direct, use consistent XML-style tags, include few-shot examples, put context first and the instruction last.
- **Model roles.** 3.6 Flash targets code generation and agentic planning. 3.5 Flash-Lite targets structured extraction and high-volume subagent work.

## 5. Lessons from Codewars

From Codewars' authoring guidelines and an open-sourced JavaScript example:

- A challenge is three strings under a type key: `initial` (starter), `answer` (hidden reference), `fixture` (hidden tests). Types in the sample: algorithms, bug fixes, refactoring, reference.
- One labelled test per requirement, plus edge cases. Failure messages should show the call and the expected value.
- Do not require what cannot be tested (for example, "use flatMap"). Hints may suggest methods but cannot enforce them.
- Visible expected values invite hard-coding. Codewars defends with random and hidden tests; we use a hidden dataset.
- The reference solution must be unreachable from user code (see the security gap above).
- Community beta testing and curation catch what automation misses. Our equivalents are the blind solver and a problem-report flag.

## 6. Platform design decisions

### Scope

- **JavaScript first.** Java comes later and needs a JDK sandbox image; `sandbox-images/java/Dockerfile` is empty today.
- **Difficulty** defaults to easy. It scales by task complexity and, for bug-fix exercises, by how subtle the bug is.
- **Categories** come from a fixed set of eight (for example imperative, functional, OOP, data structures). Each needs a one-line definition that goes into the prompt. The full list is still to be written.

### Exercise structure

An exercise is **a shared dataset plus at most two tasks.**

- The dataset is generated by Gemini for each form submission.
- **One hidden dataset** with the same shape but different values is generated alongside it. This defeats hard-coding.
- Task functions take the data as a parameter, so hidden tests can swap in the hidden dataset.
- Ordering and tie-breaking rules must be explicit in the spec. Unstated rules cause the ambiguity failures seen in the spike.
- **One list of hints for the whole exercise**, returned in the response JSON and revealed by the user on demand. Hints are visible to the client by design, so they must not contain the solution.

### Response shape

What the frontend receives:

```json
{
  "type": "algorithms",
  "title": "Order processing with array pipelines",
  "statement_md": "...background and context...",
  "dataset": { "name": "orders", "value": [ ] },
  "tasks": [
    { "id": "distinctProducts",
      "initial": "function distinctProducts(orders) {\n\n}",
      "description": "Get all distinct product names, sorted alphabetically.",
      "examples": [{ "args": ["orders"], "output": ["Keyboard", "Laptop"] }] }
  ],
  "hints": ["flatMap", "new Set", "reduce with an object accumulator"]
}
```

Server-only: each task's `answer` and `fixture`, the hidden dataset, the spec, the check results, and provenance. This follows the hidden-suite privacy invariant in [05-data-model-api.md](05-data-model-api.md).

### Exercise types

| Type | Plan |
|---|---|
| Algorithms | Supported by the spike. |
| Bug fixes | Next. Inject a bug into the reference and use that as `initial`. The existing starter-fails check proves the bug is detectable, and difficulty scales with bug subtlety. |
| Refactoring | Deferred. Hard to test; needs behavior-preservation tests plus a check on the new structure. |
| Reference | Skipped. Low value to generate. |

Whether the form exposes type as a second axis next to topic is undecided.

### Generation pipeline

1. One call produces the dataset, the hidden dataset, and up to two task specs.
2. Each task runs through the spike pipeline: spec, template, author, blind solver, five checks.
3. The exercise is accepted only if every task passes. A failed task is regenerated alone, not the whole exercise.
4. Generation is asynchronous, with progress shown to the user, as [02-architecture.md](02-architecture.md) already assumes. Expect about double the spike's per-kata cost (roughly 13,000 tokens) for two tasks; end-to-end latency was not measured.

Failures multiply across tasks, which is why the maximum is two.

### Shared corpus

- **Only exercises that pass every check are stored.** Users can come back to their exercises.
- Users either **browse** stored exercises filtered by category, difficulty (and type), or **generate** a new one within the fixed categories.
- Because categories are fixed, browsing is plain filtering. Text search and pgvector (phase 2 in the docs) can wait.
- **Diversity control.** Before generating, show the model the titles and subtopics already stored for that category and difficulty, and ask for something different. This addresses the near-duplicate generations seen in the spike.
- **Progress is per user.** Exercises are shared; attempts, submissions, and results belong to the user. This fits the existing sessions and submissions tables.
- **Browsing defaults:** exercises the user has not attempted, ordered by quality signals (`use_count`, pass rate from `validation_stats`).
- **Provenance:** store models, thinking levels, check results, and token counts per exercise (the `generation_jobs` ledger).
- **Nudge before generating.** Show how many exercises already match, which lets the generation quota be less strict than the 5 per day in [04-ai-and-retrieval.md](04-ai-and-retrieval.md).
- **Quality risk.** A flawed stored exercise is served to everyone. A problem-report flag with automatic demotion is a lightweight answer; whether it ships in v1 is open.

## 7. Prerequisites in the current repo

- **Migration bug.** In `V1__init.sql`, `test_suites` has a `programming_language` column but its CHECK constraint refers to `language`, so the migration should fail on first run.
- **Schema gaps.** The documented `categories`, `tags`, and `generation_jobs` tables do not exist yet, and `katas` has no `category_id`. There is no concept of an exercise with a dataset, several tasks, and hints, so a new `exercises` table is needed (likely a JSONB payload with the hidden parts in a server-only column).
- **Java runner image** is empty, so Java is blocked until it is built.

## 8. Open questions

1. The full list of the eight categories, with one-line definitions.
2. Does the form expose the type axis (algorithms, bug fixes), or only topic and difficulty?
3. Keep failed generations as drafts for debugging, or discard them?
4. Ship the problem-report flag in v1?
5. Hints: one flat list, or tiered from nudge to method name?
6. Show the user plain `function name(params) {}` and append the `export` at run time (proposed, not decided), or keep `export` visible?
7. Per-user generation quota, given a shared corpus.

## 9. Suggested next steps

1. Encode spec examples as one JSON string per argument, which removes the double-nesting trap (3 of the 5 round-4 failures).
2. Hand-write concept specs that pin semantics and include an example that separates the readings (the other 2 failures).
3. Rerun with 20 katas so a pass rate means something.
4. Consider raising the blind solver's thinking level; it runs on `minimal` today.
5. Prototype the two-task exercise with a dataset and a hidden dataset in the spike.
6. Prototype the bug-fix type.
7. Close the suite-readability gap before any real user touches the sandbox.
8. Then persistence: the `exercises` table, the fixed migration, and an asynchronous generation endpoint.

## Appendix: autoresearch experiment

Before the generation spike we tried Karpathy-style autoresearch on `runner/test-sandbox.js` (branch `autoresearch/sandbox-speed`): an agent edits one file, runs a fixed benchmark, keeps the change if the metric improves, and reverts otherwise. The benchmark ran the sandbox five times and took the median, gated by `runner/security-check.js`.

Seven experiments ran before we stopped. One change was kept (overlapping the post-exit `inspect()` with draining the logs). The decisive finding was about measurement: the unchanged baseline measured 1374 ms at the start and 1600 to 1800 ms later, so keep/discard decisions made against different moments were not trustworthy. Paired reruns showed the kept change was probably a small gain at best. The lesson is to compare candidate and baseline interleaved in the same session, and to use a threshold above the noise floor, before trusting an autonomous loop on timing metrics.
