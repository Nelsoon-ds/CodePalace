State and data flow

Every REST read and write is a TanStack Query query or mutation in src/api/hooks.ts. The API client adds the in-memory bearer token, handles 401 responses, and coordinates a single refresh attempt. Workspace and kata responses accept either a direct list or a conventional paged content/items envelope.

const saveDraft = useMutation({
  mutationFn: (code: string) =>
    apiRequest(`/api/sessions/${sessionId}/draft`, {
      method: "PUT",
      body: JSON.stringify({ code }),
    }),
});

Zustand is limited to interface state: whether the console is open and the draft save indicator. Persistent practice data remains server-authoritative. The Yace instance and undo history are mounted once per selected session.

Autosave and editor

CodeEditor.tsx creates Yace with its bundled code highlighter and history, indentation, tab, and bracket-pair plugins. On load, content precedence is draft, most recent submission, then kata starter code. A timer resets on every edit and sends PUT /api/sessions/{id}/draft after 800 ms idle. Blur clears the timer and writes immediately. Save failures are shown in the editor and status bar.

saveTimer.current = setTimeout(
  () => void saveRequest.current(codeRef.current),
  800,
);

Submission sends POST /api/sessions/{id}/submissions with the current code. The returned run ID starts an authenticated event stream at /api/runs/{id}/events; the run detail query supplies persisted results.

Auth and backend alignment

The inspected controllers declare these routes: auth login/register; workspace GET/POST/DELETE; session GET, draft PUT, PATCH, submissions POST (202); kata and category GET; and run detail plus SSE events. The declared request bodies are untyped Map<String,Object> except GETs, and controller methods currently return void. Run response DTOs expose status, duration, counts, assertions, output tail, and timestamp. The shell reads sessions embedded in a workspace response because no session-list route is declared.

Backend integration gaps discovered. The controllers in the checked-out worktree are stubs with no response implementation. No refresh handler exists, and the workspace-session POST route described in docs/05-data-model-api.md is not declared in a controller. The frontend implements the documented create-session route and makes a silent /api/auth/refresh attempt only when a refresh token is returned by login; those routes need corresponding backend handlers for those flows to work. A failed refresh clears memory auth and protected screens redirect to sign-in.

The current SecurityConfig permits all /api/** routes and installs no JWT filter. The client sends bearer auth, but server-side authorization cannot be considered enforced until the backend adds its JWT authentication/authorization boundary. Auth endpoints also need to return a JSON access token (and refresh token if refresh is enabled); the checked-in stubs currently return no token. Any returned tokens remain in memory. On a 401, the client tries POST /api/auth/refresh using the in-memory refresh token, or current access token when the response provided no refresh token, then clears auth on failure.

All code execution feedback is sourced from run status/assertion fields. No suite source is included in client types, requests, or UI.

Run it

cd frontend
npm install
npm run dev
npm run build

Vite proxies /api to http://localhost:8080 by default. Override with VITE_API_PROXY_TARGET, or set VITE_API_BASE_URL for a separately hosted API.
