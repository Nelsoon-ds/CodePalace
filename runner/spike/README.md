# Kata generation spike

A one-week proof of concept: can an LLM generate a coding kata (statement, starter template, hidden test suite) that is good enough to publish, with the platform verifying it automatically?

Status: spike, not production. Nothing is persisted. Nothing here is wired to the API, database, or frontend.

## The idea in one paragraph

The user picks a category, subtopic, and difficulty. The platform asks Gemini for a **spec** (a structured contract: function name, rules, examples). From that spec it builds the **starter template** itself, then asks a stronger model to write the **statement, reference solution, and hidden test suite**. A third model call tries to solve the kata from the statement alone. The platform then runs everything in the existing Docker sandbox and only accepts the kata if five independent checks pass.

## Pipeline, step by step

```
 inputs ──► 1 spec ──► 2 template ──► 3 author ──► 4 blind solver ──► 5 validate ──► 6 output
            (LLM)      (platform)     (LLM)        (LLM)              (sandbox)       (files)
```

### Step 0 - Inputs

Hard-coded in `run.js`:

| Input | Value used in the spike |
|---|---|
| category | `algorithms` |
| subtopic | `arrays` |
| concept | neutralisation: equal magnitude, opposite sign values cancel |
| difficulty | `easy` |
| count | 10 katas per run |

### Step 1 - Spec call (`generate.js`, `spec.js`)

Gemini returns a structured spec, enforced with `responseSchema`:

- `title`, `tags`
- `function_name`, `param_names`, `return_type`
- `rules`: precise enough that two correct implementations cannot disagree
- `examples` and `edge_cases`: each has `input_json` and `output_json`, which are JSON **encoded as strings** so inputs can have any shape

The platform decodes those strings into a canonical spec object (`normalizeSpec`). The spec is the single source of truth for every later step.

Model: `GEMINI_MODEL`, thinking level `high`.

### Step 2 - Template (`template.js`)

The platform, not the LLM, builds the starter code from the spec:

```js
export function neutralise(arr) {
  throw new Error("Not implemented");
}
```

The signature cannot drift from the spec because no model writes it.

### Step 3 - Author call (`generate.js`, `spec.js`, `example-kata.js`)

A stronger model receives the spec and returns four fields via `responseJsonSchema`, in this order:

1. `rule_coverage`: one line per rule and edge case, mapping it to the test that covers it
2. `statement_md`: the problem statement the user will read
3. `reference_solution`: complete `src/solution.mjs`
4. `test_suite`: complete `tests/suite.test.mjs` (vitest)

Prompt structure (follows Google's Gemini 3 prompting guidance): constraints first, one hand-written few-shot example (`example-kata.js`, a different concept on purpose), then the real spec, then one instruction anchored with "Based on the specification above...".

Model: `AUTHOR_MODEL`, thinking level `high`.

### Step 4 - Blind solver (`blind.js`)

A separate call receives **only the statement and the template**. No suite, no reference. It writes its own solution. If that solution passes the hidden suite, the statement is sufficient to solve the kata. This is the automated version of Codewars' community beta testing.

Model: `GEMINI_MODEL`, default thinking.

### Step 5 - Validation (`validate.js`)

Runs in the real sandbox via `runInSandbox` from `runner/test-sandbox.js`. Five checks:

| Check | Passes when |
|---|---|
| `reference_passes` | The reference solution passes every test in the suite |
| `starter_fails` | A throwing stub fails the suite |
| `examples_match_reference` | Example tests **generated by the platform** from the spec's examples and edge cases pass against the reference. This catches wrong examples and wrong call encodings |
| `mutations_fail` | At least one mutation of the reference is caught by the suite (skipped if the reference itself fails) |
| `blind_solver_passes` | The blind solver's solution passes the hidden suite |

A kata is published only if all five pass. Mutations are three regex rewrites (constant return, inverted condition, off-by-one). They are weak: a surviving mutant is often equivalent, so the check only requires one kill, not all.

### Step 6 - Output (`run.js`)

For each kata, one JSON file with two sections:

- `ui`: what a frontend would receive. Title, statement, template, examples, tags, difficulty. **No suite, no reference.**
- `private`: server-only. Spec, `rule_coverage`, reference, suite, blind solution, check details.

Plus `results.csv` with one row per kata. The latest export is saved here as `results.csv`.

## Running it

Needs Docker running, the `codepalace/runner-node:22` image, and Node 22+. In `.env`:

| Variable | Purpose |
|---|---|
| `GEMINI_API_KEY` | API key |
| `GEMINI_MODEL` | Model for the spec call and blind solver (used: `gemini-3.5-flash-lite`) |
| `AUTHOR_MODEL` | Model for the author call (used: `gemini-3.6-flash`) |
| `SPEC_THINKING_LEVEL`, `AUTHOR_THINKING_LEVEL` | Optional. Default `high` |

```
node runner/spike/run.js
```

Output goes to `/tmp/opencode/spike/<timestamp>/`.

## Model settings, and why

Taken from Google's Gemini API docs:

- **No `temperature`, `top_p`, or `top_k`.** Deprecated on Gemini 3.x. Ignored on 3.6 Flash and 3.5 Flash-Lite; newer models return HTTP 400.
- **Thinking level is the quality dial.** 3.5 Flash-Lite defaults to `minimal`, close to no reasoning. 3.6 Flash defaults to `medium`. Do not combine `thinkingLevel` with `thinkingBudget`.
- **Structured output follows schema key order.** Hence `rule_coverage` is the first field in the author schema. Make all fields required.
- **Schema-constrained output is always valid JSON**, which removed the "Bad control character" parse failures seen without a schema.
- **Always include few-shot examples** and put instructions after the context.

| Round | Setup | Result | What it showed |
|---|---|---|---|
| 1 | One call writes everything. Free-text themes (palindromes, parsing, counting). `gemini-3.5-flash-lite` | 8 of 10 passed | Validation caught a wrong test expectation and a reference containing prose instead of code |
| 2 | Spec-first pipeline, `flash-lite` as author. Neutralisation | 1 of 5 passed | Reference and suite disagreed about the rule, and the checks caught it |
| 3 | Author switched to `gemini-3.6-flash` | 8 of 10 passed. 2 failed before validation (JSON parse). All 8 generated katas passed | The author model was the bottleneck |

### Latest run (round 4) in detail

| Check | Passed |
|---|---|
| `reference_passes` | 10 of 10 |
| `starter_fails` | 10 of 10 |
| `mutations_fail` | 10 of 10 |
| `examples_match_reference` | 7 of 10 |
| `blind_solver_passes` | 8 of 10 |

Why the 5 failures happened:

- **Three katas had broken spec examples.** Two used the wrong argument nesting (`[1,-1,2]` instead of `[[1,-1,2]]`, or `[]` instead of `[[]]`), so the function received the wrong arguments. One example was simply wrong arithmetic.
- **Two katas hit an ambiguity in the concept.** Eight of ten references use stack-top matching. Two use "search for the most recent matching value", which returns `[2]` for `[1, 2, -1]`. The blind solver wrote the stack-top version and failed those suites. The concept text I wrote allows both readings.

Cost: about 2,850 input, 1,550 output, and 8,800 thinking tokens per kata. Thinking tokens (5,700 to 14,300) are about six times the output.

The author step was solid in this run, with no check failures attributable to it.

## Known limitations

- **Hidden suite is readable inside the sandbox.** User code runs in the same container as `tests/suite.test.mjs` and can read it. Verified with a probe. Fine for a demo, not for a real product. Options in the design docs: deliver the suite over stdin, or a trusted harness outside the user's container.
- **Weak mutation testing.** Regex mutants can be equivalent to the original, so the check requires only one kill.
- **Sample sizes are small.** Ten katas per run cannot tell whether one change helped. Several settings changed at once in round 4.
- **Spec example encoding is fragile.** One JSON string per whole argument list invites double-nesting mistakes.
- **Statement gaps are not checked.** A suite can test a behavior the statement never mentions. The blind solver only catches this when it happens to read the statement differently.
- **Single language, single concept.** JavaScript only. Neutralisation only. No persistence, auth, or frontend.

## Suggested next steps

1. Encode examples as one JSON string **per argument** to remove the double-nesting trap. This addresses 3 of the 5 round-4 failures.
2. Hand-write the concept spec: pin whether matching is stack-top or search, and include an example that separates them, such as `[1, 2, -1]`. This addresses the other 2.
3. Rerun with 20 katas so a pass rate is meaningful.
4. Consider raising the blind solver's thinking level. It runs at the default (`minimal`) on Flash-Lite and may be pattern-matching to familiar idioms.
5. Only then: persistence, then the API and UI. See `docs/04-ai-and-retrieval.md` and `docs/05-data-model-api.md`.

## Where this fits in the design docs

- `docs/04-ai-and-retrieval.md` describes the generate, validate, retry loop. This spike adds a spec step and the blind solver, and does not implement the retry loop.
- `docs/05-data-model-api.md` defines the privacy rule that suites never reach the browser. The `ui` / `private` split in the output follows it.
- The structure of one test per rule, edge cases, and clear failure messages follows Codewars' authoring guidelines.
